# ReelForge

**Build videos with Flutter.** Write a composition as widgets, scrub it with
hot reload, then render it to MP4 — on your machine, in CI, or from inside a
running app on someone's phone.

This is **not** a screen recorder. A composition is a deterministic function of
frame number: `data → widgets → frames → MP4`. Frame 900 produces the same
pixels whether you played forward to it, scrubbed backward to it, or rendered
it alone on another machine an hour later.

```dart
final Composition promo = Composition(
  id: 'Promo',
  width: 1080,
  height: 1920,
  fps: 30,
  durationInFrames: 90,
  builder: (BuildContext context) {
    final int frame = Video.frame(context);
    return Stack(children: <Widget>[
      ProductCard(product: product),          // your app's own widget
      Positioned(
        bottom: interpolate(frame, <int>[0, 30], <int>[0, 100]),
        child: Text(product.name),
      ),
    ]);
  },
);
```

```bash
reelforge render --composition Promo --out promo.mp4
```

## Why

Video is the last thing in a product that is still made by hand. Everything
else — screenshots, PDFs, emails, dashboards — is generated from data. Video is
where someone opens an editor, drags a number onto a timeline, and does it
again next week when the number changes.

Compositions are code, so they take data as input. The weekly report renders
itself. And because they are *Flutter* widgets, the components are the ones
your app already has: the same card, the same chart, the same fonts and theme,
not a redrawn approximation of them.

## Getting started

Requires Flutter 3.35+ and ffmpeg for the CLI. macOS is the developed and
tested path today.

```bash
dart pub global activate reelforge_cli

cd my_app
reelforge init --fix-entitlements   # writes a composition and two entry points
flutter pub get

reelforge preview                   # scrub it, with hot reload
reelforge render --composition Intro --out intro.mp4
```

`init` writes nothing over anything, so running it twice is safe.

## Compositions in JSON

The same vocabulary, serialisable — so a composition can be written by a
designer, sent by a server, or generated by a model, and still render through
exactly the same widgets:

```bash
reelforge render reel.json --data report.json --out reel.mp4
```

Documents are data, so checking one needs no Flutter and no build:

```bash
reelforge validate reel.json --data report.json
```

Given `--data` it answers the second question too — whether that data actually
fills the document's bindings. A document and its data can each be valid and
still render nothing together, which is how you get sixty seconds of empty
scenes and an exit code of zero.

## Export from inside your app

The CLI shells out to ffmpeg. An app on someone's phone cannot — so
`reelforge_encoder` encodes with the device's own hardware:
`AVAssetWriter` on iOS and macOS, `MediaCodec` on Android. No ffmpeg, no
server, no upload.

```dart
await InAppExporter.export(
  composition: composition,
  encoder: NativeVideoEncoder(),
  outputPath: path,
);
```

A 60-second reel — 1800 frames at 1080×1920, three looping video clips, eight
sounds — exports in **13.6 s inside an app**, 4.4× realtime, under 450 MB RSS.
Mean SSIM against the ffmpeg render is 0.998.

## The packages

| package | what it is |
|---|---|
| [`reelforge`](https://pub.dev/packages/reelforge) | the engine: compositions, sequences, media, preview, render host |
| [`reelforge_kit`](https://pub.dev/packages/reelforge_kit) | ready-made scenes, charts and motion primitives |
| [`reelforge_json`](https://pub.dev/packages/reelforge_json) | the JSON document format and its runtime interpreter |
| [`reelforge_schema`](https://pub.dev/packages/reelforge_schema) | the format's parsing and validation, with no Flutter dependency |
| [`reelforge_cli`](https://pub.dev/packages/reelforge_cli) | `init`, `preview`, `render`, `validate`, `inspect`, `list` |
| `reelforge_encoder` | on-device encode and decode (unpublished) |

## Status

Pre-alpha, and honest about it — but it works end to end, and the claims above
are measured rather than estimated:

- Determinism is **byte-exact** across isolated renders and across scrubbing.
- A 60-second eight-scene reel renders at **5.8× realtime**; sharding across
  four processes is the knee.
- Video clips land on the **exact source frame**, identically across 1, 2, 4
  and 8 shards, verified per frame by pixel value rather than by eye.
- Two real third-party apps have hosted a render, including a plugin-heavy one
  with a Rust cdylib.
- **370 tests** across the six packages.

Not yet: Windows and Linux are untested, Android is verified on an emulator
rather than real hardware, and the API will change.

The numbers, the methodology and everything that did not work are in
**[the guide](docs/guide.md)** — including the benchmarks you can reproduce.
